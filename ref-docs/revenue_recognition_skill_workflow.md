# 收入确认 Skill 业务工作流

## 文档定位

本文档描述整个收入确认 Skill 的业务工作流、上下游交接物和职责边界。

它是仓库级参考文档，不是单个 feature 的实现规格，也不替代
`specs/001-revenue-rollup-cli/` 下的 Speckit 工件。

当前 `001-revenue-rollup-cli` 只覆盖十步 SOP 中的第 3 步“汇总”。

## 业务目标

收入确认 Skill 的目标，不是让 Agent 自行发明会计确认逻辑，而是把标准化、机
械化、可审计的工作步骤串起来：

- 对平台导出的原始文件做整理
- 将流水级数据稳定汇总为门店级基础事实字段
- 把最终收入确认规则继续留在飞书多维表配置中
- 将确认结果用于后续入账、核对、分发、调整和封版

核心原则是：

- 汇总自动化
- 确认规则透明化
- 会计计量可追溯
- Agent 不越界替代业务判断

## 十步 SOP 总览

| 步骤 | 名称 | 主要目标 | 主要输入 | 主要输出 | 当前仓库关系 |
|---|---|---|---|---|---|
| 1 | 下载源文件 | 从平台获取本期原始业务文件 | 平台导出能力、期间信息 | 原始下载目录或压缩包 | Skill 上游业务步骤 |
| 2 | 文件预处理 | 解压、识别、分拣出当前确认项目可消费的干净输入 | 原始下载目录、确认项目 | 干净源文件目录或单文件 | Skill 上游业务步骤 |
| 3 | 汇总 | 将流水级数据按门店和规则汇总并上传业务数据库 | 预处理后源文件、规则、期间 | 门店级基础事实字段、汇总结果文件、业务数据库记录 | 当前 `001-revenue-rollup-cli` feature |
| 4 | 收入回款确认 | 在飞书多维表中通过字段间运算形成确认结果 | 汇总结果记录、查找引用、公式字段 | 折后收入、实际回款、平台服务费、税费、配送费等确认结果 | Skill 下游业务步骤 |
| 5 | 后处理 | 对业务表做小修小补，保证后续链路可用 | 确认结果、业务表记录 | 修正后的业务表数据 | Skill 下游业务步骤 |
| 6 | RPA 入账 | 将确认结果录入记账软件 | 已确认结果、RPA 流程 | 记账系统入账结果 | Skill 下游业务步骤 |
| 7 | 验算 | 对确认及入账结果做复核 | 确认结果、记账结果 | 验算结论 | Skill 下游业务步骤 |
| 8 | 分发 | 将结果分发给各核算主体会计做后续动作 | 确认结果、验算结果 | 分发记录 | Skill 下游业务步骤 |
| 9 | 调整 | 在规则变更或业务修正时重算并更新结果 | 问题结论、调整口径 | 调整后结果 | Skill 下游业务步骤 |
| 10 | 封版 | 形成最终留档版本 | 调整后结果、分发和验算状态 | 封版结果 | Skill 下游业务步骤 |

## 各步骤详细说明

### 1. 下载源文件

这一步的目标是把平台原始文件拿到本地或工作区。

需要注意：

- 平台下载结果通常是“一个平台下有多种业务文件”，而不是“一个文件里混着多种业务表”
- 可能是压缩包，也可能是多个 Excel / CSV 文件
- 这一步不要求 Agent 已经知道哪个文件能直接用于当前确认项目汇总

### 2. 文件预处理

这一步的目标是把原始下载结果转成汇总工具可消费的干净输入。

典型动作包括：

- 解压压缩包
- 识别同一平台下不同业务文件的类型
- 按确认项目进行分拣
- 将当前确认项目真正需要的那一类文件单独整理到专用目录

示例：

- 在 `202605-source-excel/美团团购/` 下，可能同时存在“收益列表”和“收益明细”
- 如果当前项目是“美团团购回款确认”，预处理阶段应将“收益列表”单独拎到一个干净目录
- 之后 `run_recog_rollup --source_file` 才消费这个干净目录，而不是直接消费原始下载目录

### 3. 汇总

这一步是当前仓库 `001-revenue-rollup-cli` feature 的职责范围。

它的目标是：

- 读取预处理后的单文件或目录
- 按确认项目规则做结构检验
- 对流水级数据按门店和规则做汇总
- 将结果写入结果文件并上传业务数据库（飞书多维表）

它的产物是：

- 门店级基础事实字段
- 可追溯的 preview 结果文件
- 业务数据库中的汇总记录

它不是最终收入确认结果。

### 4. 收入回款确认

这一步的目标是在飞书多维表中完成真正的收入确认与回款确认。

关键特点：

- 主要是字段间运算
- 依赖飞书多维表中的查找引用、公式字段等配置
- 汇总步骤提供的是“字段原材料”，而不是最终结果

典型下游字段包括：

- 折后收入
- 实际回款
- 平台服务费
- 税费
- 配送费

这一步之所以不塞进汇总工具，是为了：

- 保持确认规则由用户配置和控制
- 保持过程透明、可解释、可审计
- 避免 Agent 幻觉直接介入严谨的会计计量

### 5. 后处理

这一步的目标是对业务数据库中的记录做必要的小修小补。

典型场景包括：

- 新增门店 id，需要补充到门店映射表
- `来源文件` 字段当前还是 raw 文件名，需要改成对应账号主体中文名

这一步消费的是汇总后或确认后的业务表记录，不属于汇总引擎本体。

### 6. RPA 入账

这一步调用 RPA 将已确认结果录入记账软件。

它依赖的是已经确认完成的结果，不是原始流水或汇总中间结果。

### 7. 验算

这一步对确认与入账结果做复核，判断是否存在计算、映射或执行错误。

### 8. 分发

这一步将确认结果分发给各核算主体会计，用于后续银行对账等工作。

### 9. 调整

这一步用于处理规则变化、业务修正或上游数据变化引发的重新运算。

它通常意味着：

- 回到飞书配置或上游数据治理
- 必要时重新执行预处理、汇总、确认链路

### 10. 封版

这一步形成最终留档版本，标志当前期间的收入确认工作闭环完成。

## Agent 视角的完整执行链路

当 Agent 要把一个确认项目从头到尾做好时，合理的执行方式是：

1. 明确本期确认项目、平台和期间
2. 下载平台源文件
3. 完成文件预处理，得到可交给 `source_file` 的干净输入
4. 调用 `list_recog_items` 判断当前应使用的 `recog_id`
5. 调用 `run_recog_rollup` 完成结构检验、试算和上传
6. 在业务数据库中确认汇总原材料已经就位
7. 理解下游收入回款确认如何基于这些字段继续计算
8. 视需要执行后处理、RPA 入账、验算、分发、调整与封版

关键边界是：

- 如果问题出在文件没解压、文件类型没分拣、目录还不干净，属于步骤 2 的问题
- 如果问题出在门店汇总口径、规则读取或上传行为，属于步骤 3 的问题
- 如果问题出在折后收入或实际回款怎么得出，属于步骤 4 的问题
- 如果问题出在映射修正、主体名称修正，属于步骤 5 的问题

## 交接物矩阵

| 上一步 | 交给下一步的核心产物 | 说明 |
|---|---|---|
| 下载源文件 -> 文件预处理 | 原始下载目录 / 压缩包 | 还不能直接用于汇总 |
| 文件预处理 -> 汇总 | 干净源文件目录 / 单文件 | 这是 `source_file` 的正确语义 |
| 汇总 -> 收入回款确认 | 门店级基础事实字段 | 下游继续做字段间运算 |
| 收入回款确认 -> 后处理 | 已确认结果及相关业务表记录 | 进入小修小补与治理 |
| 后处理 -> RPA 入账 | 可入账的最终确认结果 | 进入记账系统 |
| RPA 入账 -> 验算 | 入账结果与确认结果 | 用于复核 |
| 验算 -> 分发 | 可对外使用的确认结果 | 分发给各主体会计 |
| 分发 / 调整 -> 封版 | 最终确认结果与变更痕迹 | 形成封版留档 |
