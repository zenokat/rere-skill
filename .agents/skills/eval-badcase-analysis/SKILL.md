# 评测 Badcase 分析

## 核心定位

对评测运行的失败 case 做深入分析，输出结构化的 badcase 分析报告。分析必须挖到根因，改进方向必须基于产品代码的当前状态提出有根据的建议。

## 分析原则

### 1. 自主驱动，挖到底

分析 badcase 就是一直挖到底，顺着自己的思路和新的发现一直挖下去，直到你自己觉得分析到位了，能指示出接下来产品的迭代方向。**不要以用户为中心总是询问用户的意见，以你自己为主。** 遇到不确定的地方，先自己查代码、看 trace、做对比，而不是停下来问用户。

### 2. 结论先行

每个类型的分析结构固定为：**涉及 case -> 根因（结论先行）-> 改进方向 -> 证据链**。先给出结论，再展开证据。读者（通常是产品经理）应该能在每个类型的前三段理解发生了什么、为什么、怎么办。

### 3. 落到产品代码

所有 badcase 分析最终都要落到"改进方向"上。这意味着**必须看当前产品的代码实现**，结合当前状态去分析根因，提出有根据的（而非不看产品就瞎指挥的）改进方向建议。脱离产品代码的泛泛分析没有价值。

### 4. 先分类再逐个深入

面对多个失败 case 时，先根据错误模式归类（而不是逐个线性分析），再逐类深入。分类的标准不是表面现象（如"产物为空"），而是根因类型（如"Agent 偏离路径"、"脚本卡死"、"源文件给错"）。

## 分析流程

### 第一步：全局概览

从 `batch.json` 获取评测批次的基本信息（总 case 数、通过/失败数、总耗时、总 token）。从 `result.json` 列出所有失败 case 及其 grader 评分。

### 第二步：归类失败 case

阅读每个失败 case 的 `result.json`（grader 评分和 summary）和 `session.jsonl`（Agent 执行轨迹），根据根因将失败 case 归为不同类型。

归类的线索：
- Agent 最终回复中描述的行为（走了什么路径、卡在哪里）
- grader 的失败原因（file missing、sheet missing、field mismatch 等）
- 产物是否存在、格式是否预期

### 第三步：逐类深入分析

对每个类型，按"涉及 case -> 根因 -> 改进方向 -> 证据链"的结构写分析。

**根因分析的核心方法：**

1. **读 session trace**：逐行阅读 `session.jsonl`，还原 Agent 的决策路径。注意 Agent 在每个关键节点的 reasoning（为什么要这样做，放弃了什么替代方案）。

2. **看产品代码**：根因分析必须回到产品代码。如果怀疑脚本卡死，去读脚本的实现，搞清楚执行链路、网络调用、文件操作，从代码中找到证据。如果怀疑 Agent 偏离路径，去读 SKILL.md 和 skill 的 references，搞清楚正确路径是什么，Agent 在哪一步偏离了。

3. **做对比**：找通过的 case 与失败 case 做对比。通过的 case 做对了什么？失败 case 做错了什么？差异是 Agent 行为差异还是运行时条件差异？对比时要验证假设而非猜测——比如"pipe 导致失败"的假设，需要检查通过 case 是否也有 pipe。

4. **否定假设**：每提出一个假设，先想怎么否定它，再去找否定证据。被否定的假设也要记录在分析中（作为"排除的因素"），帮助读者理解为什么结论是现在的样子。

5. **画时间线**：如果 case 是串行执行的，画出执行时间线。这能暴露"飞书 API 限流"等时序相关的假设是否成立。

### 第四步：提出改进方向

改进方向必须：
- **具体到代码位置**：指出要改哪个文件的哪个方法，而不是泛泛说"优化性能"
- **基于产品当前状态**：改进建议必须建立在对产品代码的理解之上
- **可验证**：改进后的预期效果要可衡量（如"通过率从 X% 提升到 Y%"）

## 报告结构

```
# {评测集名称} Badcase 分析

## 失败总览（全局概览 + 类型分类表）

## 类型 X：{类型名称}

### 涉及 case（表格：case、outputs、最终回复、耗时）

### 根因（结论先行，2-3 句话概括根因）

### 改进方向（具体到代码位置，按优先级排序）

### 证据链（trace 分析、代码引用、对比数据、时间线、否定假设）

## 迭代方向总结（按 P0-Pn 优先级排序的改进项汇总）

### 修复后的预期效果
```

## 输出规范

- 分析报告写为 Markdown 文件，命名为 `badcase_analysis.md`，放在评测结果的批次目录下
- 结论先行：每个类型的前三段（涉及 case + 根因 + 改进方向）应该能让读者快速理解核心信息
- 证据链详实但不冗余：用表格、代码引用、时间线等结构化方式呈现证据，而非大段叙述
- 不需要做的事也要写：明确记录哪些方向被排除以及为什么，避免后续重复讨论

## 典型失败类型参考

以下是常见的评测失败类型及其分析要点（具体案例参考 `references/badcase-patterns.md`）：

| 类型 | 典型表现 | 分析要点 |
|---|---|---|
| Agent 偏离 skill 路径 | 产物格式不符预期 | 读 trace 找偏离点；看 SKILL.md 是否可被 Agent 读到；对比同条件通过的 case |
| 脚本/工具执行卡死 | outputs 为空或 Agent 放弃轮询 | 读产品代码的执行链路；分析网络调用和超时配置；看 stdout/stderr 输出行为 |
| 源文件/配置给错 | Agent 正确阻断但被判 fail | 结合 suite 的评测目的判断；区分 Agent 行为问题和 case 数据问题 |
| grader 判定有误 | Agent 行为正确但 grader 判 fail | 检查 grader 逻辑；区分 grader bug 和 grader 设计意图 |

## 边界规则

- 不在分析阶段提出代码修复 PR，只给出改进方向建议
- 不修改评测结果数据（result.json、session.jsonl、outputs/）
- 当 evidence 不足以确定唯一根因时，列出所有可能根因并标注置信度，而不是强行选一个
- 分析报告是给产品决策者看的，避免纯工程术语，用产品经理能理解的语言描述根因和影响
